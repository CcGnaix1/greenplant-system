## 二、测试策略

### 2.1 分层设计

| 层次 | 方法 | 用例数 |
|---|---|---|
| 接口功能测试 | 黑盒，按业务模块划分 8 组 | 62 |
| 识别准确率测试 | 白盒取验证集，端到端跑部署模型 | 3 轮（野外 542 + 室内验证 596 + 室内测试 596）|

### 2.2 用例设计方法

- **等价类划分**：每个接口按「合法 id / 不存在 id（999999）/ 非法类型（abc）/ 缺失参数」划分四类输入；
- **边界值分析**：上传文件取 0 字节（空文件）、超限（11MB > 10MB 上限）两个边界；
- **错误推测**：针对已知设计（AI 未就绪回退 mock、路径越界 403 守卫）设计专项用例；
- **契约一致性检查**：以接口清单声明的 `{code,msg,data}` 与状态码语义为准，检查同类错误的 code 归类是否一致。

### 2.3 准确率测试口径（关键设计决策）

项目的 `ml/evaluate.py` **在全部 2708 张图上评估**，其中 2166 张是训练集，会把准确率刷到约 0.99 —— 这个数字**不能**用于论证泛化能力。

因此本报告的口径是：

> 复现 `train.py` 的训练/验证切分（`seed=42`、`train_split=0.8`），
> **只取验证集 542 张**（训练时模型从未见过）评估推理服务实际加载的 `plant_model.onnx`。

复现方式不是自己写 `randperm`，而是调用与训练时**同一个** `random_split` 并读取其 `indices`，保证逐样本一致 —— 实测 Top-1 与训练日志报告的 `val_acc` 完全吻合（偏差 0.0000），可以确认切分正确。

### 3.2 通过项中的重点结论

- **统一契约成立**：所有正常与业务异常（4001 参数错误、4040 不存在）都稳定返回 `{code,msg,data}` 且 HTTP 200，与前端 `request.js` 只认 `code` 字段的实现相匹配。
- **闭集分类对齐**：`GET /knowledge/list` 恰好 20 个品种，与模型 20 类一致 —— 这是识别结果能查到品种描述的前提（少一行会导致前端 `desc` 为空）。
- **路径越界防护有效**：`POST :5000/recognize` 传数据集路径返回 403，任意文件读取被正确挡住。
- **鉴权为「演示态」**：`AuthInterceptor` 对无效/缺失 token 一律回落 `DEMO_USER_ID=1`，**永不返回 4010**。这在实训演示场景是合理的，但意味着接口无真实访问控制（见 5.2 观察项）。
- **诊断确实不走模型**：`/diagnose/checklist` 按勾选症状查字典拼报告（`confidence` 由勾选数量与类别跨度推算：≤2 个 0.90、≤4 个 0.80、跨 3 大类再压到 0.70），与文档描述一致。
- **软删语义正确**：`POST /plant/delete` 把 `archive_status` 置为 `archived`，删除后列表与详情均查不到（详情返回 4040），但数据库记录与养护记录仍在 —— 可追溯、可恢复。重复删除返回 4040 而非误报 5000。
- **统计为实时聚合**：`GET /plant/stats` 的周浇水次数直接扫 `care_record` 按周分组，0 条记录时各项为 0 且不报错（平均间隔回落到品种默认值），不存在预置常量。
- **导出文件真实可用**：`GET /plant/export` 返回的 xlsx 经校验是合法 zip、含全部必需 OOXML 部件、各 XML 均合法、行号递增、数值单元格为真数字类型；csv 带 UTF-8 BOM，Excel 打开不乱码。

## 五、缺陷与观察项

### 5.1 缺陷清单

| 编号 | 严重度 | 标题 | 关联用例 | 证据 |
|---|---|---|---|---|
| DEF-01 | 中 | 请求参数错误被归类为「服务器内部错误」(5000)，而非参数错误 (4001) | TC-P04、TC-S03、TC-K05 | 缺 `id` → `code=5000`，而同样缺 id 的 `/plant/record` 却正确返回 `4001`，同类错误归类不一致 |
| DEF-02 | 中 | 空文件上传被判为「识别成功」，返回 0.82~0.96 的高置信度假结果 | TC-S09 | 空文件 → `code=0, isMock=true, 首选=龟背竹, 置信度=0.94` |
| DEF-03 | 中 | 异常响应原样回显内部异常文本，存在信息泄露 | TC-P04/S03/K05/A03/A04 | 响应体含 `java.lang.String`、`No static resource`、`Maximum upload size exceeded` 等框架内部信息 |
| DEF-04 | 低 | 未映射路径返回 HTTP 200 + code 5000，而非 404 | TC-A03 | `/api/no-such-endpoint` → `http=200 code=5000` |
| DEF-05 | 低 | 超过 10MB 上传被拒，但报「服务器内部错误」而非明确的容量超限提示 | TC-A04 | `code=5000 msg=服务器内部错误：Maximum upload size exceeded` |

**根因分析（DEF-01 / 03 / 04 / 05 同源）**：
`common/GlobalExceptionHandler.java` 用 `@ExceptionHandler(Exception.class)` 兜底所有异常，统一转成 `code=5000` 且原样拼接 `e.getMessage()`。这一层本身是**必要**的（否则 Spring 默认 `/error` 返回的 `{"timestamp","status","error"}` 结构前端解析不出 `code`，会把失败当成功），但缺少对**客户端错误**的细分处理。

**修复建议**：

```java
// 在 GlobalExceptionHandler 中补充细分处理，且不要回显原始异常文本
@ExceptionHandler({MissingServletRequestParameterException.class,
                   MissingServletRequestPartException.class,
                   MethodArgumentTypeMismatchException.class})
@ResponseStatus(HttpStatus.BAD_REQUEST)
public Result<?> handleBadRequest(Exception e) {
    return Result.error(ResultCode.PARAM_ERROR, "请求参数不合法");   // code=4001
}

@ExceptionHandler(MaxUploadSizeExceededException.class)
@ResponseStatus(HttpStatus.PAYLOAD_TOO_LARGE)
public Result<?> handleTooLarge(MaxUploadSizeExceededException e) {
    return Result.error(ResultCode.PARAM_ERROR, "图片过大，请压缩到 10MB 以内");
}

@ExceptionHandler(NoResourceFoundException.class)
@ResponseStatus(HttpStatus.NOT_FOUND)
public Result<?> handleNotFound(NoResourceFoundException e) {
    return Result.error(ResultCode.NOT_FOUND, "接口不存在");         // code=4040
}
```

**DEF-02 修复建议**：在 `RecognizeController.recognize()` 入口补空文件校验（同项目的 `FrontDiagnoseController.uploadPhoto()` 已有此校验，可直接对齐）：

```java
if (file == null || file.isEmpty()) {
    return Result.error(ResultCode.PARAM_ERROR, "请选择图片");
}
```

### 5.2 观察项（非缺陷，但建议核对）

| 编号 | 现象 | 说明与建议 |
|---|---|---|
| OBS-01 | `POST /api/notification/read` 与 `/read-all` 已实现且测试通过，但**前端无任何调用** | 全量检索 `zhwu/**/*.js` 未见调用（`api.get/post/upload/call` 四种方式均已检索）。意味着小程序里「通知已读」功能不可达，未读数无法消除。建议核对是否漏接 |
| OBS-02 | `POST /api/diagnose/photo` 被前端调用（`pages/diagnose/diagnose.js:62`），但《运行说明.md》第四节接口清单未收录 | 文档遗漏，建议补入 |
| OBS-03 | 通知「已读」状态的三个命名不一致：数据库列 `is_read`、请求参数 `isRead`、响应字段 `read` | 易踩坑，建议统一为 `isRead` |
| OBS-04 | `GET /api/knowledge/detail` 只返回养护详情，**不含品种名** | 前端需依赖列表页已获取的名称渲染标题，若单独打开详情页会缺标题。建议响应中带上 `name` |
| OBS-05 | 上传落盘文件名为 `System.currentTimeMillis() + ".jpg"` | 同一毫秒内的并发上传会撞名相互覆盖。虽然实训场景几乎不会触发，但属真实缺陷隐患，建议改为 `时间戳 + 随机后缀` |
| OBS-06 | AI 服务不可用/图片损坏时回退 mock，会给出 0.82~0.96 的「高置信度」 | 前端未展示 `isMock` 字段（`pages/scan/scan.js:30`），用户无法分辨真假识别。建议后端在 mock 时降低置信度或前端提示「演示模式」 |

## 六、测试结论

### 6.1 结论汇总

| 测试项 | 结果 |
|---|---|
| 接口功能测试 | **45/51 通过（88.2%）**，6 条失败全部为真实缺陷，无接口崩溃 |
| 识别准确率（Top-1） | **0.9096**，与训练报告完全一致 |
| 识别准确率（Top-3） | **0.9631** |
| ONNX 导出保真性 | **通过**（预测一致率 1.0000） |
| 缺陷数 | 5 个（中 3 / 低 2），无「严重」「致命」级缺陷 |

### 6.2 质量评价

- **核心链路可用**：端到端「小程序上传 → 后端落盘 → 推理服务识别 → 回写数据库 → 返回候选列表」全链路正常，真实图片识别置信度 0.9036，非 mock。
- **契约稳定**：统一 `{code,msg,data}` 结构在正向与业务异常下均成立，前端可依赖。
- **模型质量达标**：Top-1 0.9096 / Top-3 0.9631，对 20 类闭集分类任务属良好水平；导出环节无损，部署与训练一致。
- **主要短板在错误处理**：5 个缺陷中有 4 个同源于 `GlobalExceptionHandler` 未细分客户端错误，且回显内部异常文本。修复集中在一个类中，成本低、收益高。
- **最值得注意的是 DEF-02**：空文件上传会返回一个「94% 置信度的龟背竹」假结果，这是唯一可能误导最终用户的缺陷，建议优先修复。

### 6.3 局限性与后续建议

1. **准确率 0.9096 是「规整照片」下的成绩**。验证集图片来自 iNaturalist/GBIF 采集，多为背景干净、主体突出的单株照片；而用户手机实拍常见背景杂乱、光照差、多株同框、特写叶片等情况。**真实场景准确率会低于 0.9096**，建议补采 30~50 张实拍图做一次「现场测试」。
2. **类别不平衡（2.56×，63~161 张/类）**，且验证集各类样本仅 6~35 张，小类别（袖珍椰子 6 张）指标波动大。若要提升最弱类别，建议对少数类做定向补采或加权采样。
3. **易混簇可定向优化**：吊兰/常春藤/鹅掌柴/迷迭香/铜钱草 与 茉莉花/栀子花/薄荷 两簇的混淆可通过增加这两簇的训练样本量改善。
4. 本轮未覆盖性能、并发、UI 端到端；接口测试为单机顺序执行，未验证并发下的上传撞名问题（OBS-05）。

### 8.4 关于统计页的株高曲线（如实说明的限制）

原页面画了「株高增长趋势」曲线，数据是写死的。整改时发现**无法做成真的**：
`plant_archive` 只有 `cur_height` 单值，没有高度历史表。因此该图表已移除，

要做成真实的增长曲线，需要新增一张高度记录表或一个「记录生长测量」的接口。

### 8.5 导出为什么不生成 PDF

原页面提供「PDF 报告」，但同样是假的（只弹 toast）。生成**含中文**的 PDF 必须嵌入 CJK 字体，
而本项目用 `mvn -o` 离线构建，本地 `.m2` 里没有 iText/PDFBox，加依赖会直接构建失败。
因此 PDF 选项被移除，改为 xlsx + csv 两种真实可用的格式。

XLSX 是用 JDK 自带的 `ZipOutputStream` 手写的（`common/XlsxWriter.java`）——
xlsx 本质就是 zip + 几个固定 XML，数据量小时手写完全够用，无需引入 POI。

**选 xlsx 而非只给 csv 的原因**：小程序 `wx.openDocument` 支持 doc/xls/xlsx/pdf，
**不支持 csv**；只给 csv 的话用户在小程序里点开是打不开的。csv 作为电脑端备选保留。

## 九、室内域微调（2026-09-29）

### 9.1 问题：不是「没训够」，是「没见过」

用户在 09-29 用小程序实拍两张室内盆栽，置信度只有 **0.4897 / 0.4580**，且**判错**
（水培绿萝被判成栀子花）。这不是训练不足，证据如下：

| 证据 | 数据 |
|---|---|
| 训练集已过拟合 | 最后一轮 `train_acc 0.9986` vs `val_acc 0.9059`，gap **+0.09**。继续加轮次只会让 gap 更宽 |
| 同一株绿萝换场景就崩 | 野外照 `绿萝 0.826~0.889`（全对）；用户室内照 `栀子花 0.458`（错） |
| 数据来源单一 | `ml/fetch_inat.py` 证实：2708 张全部来自 iNaturalist **野外**观察照（经 GBIF 取图，来源字段全为 `wild`）|

结论：**训练图里根本没有「室内盆栽」这一域的样本**，再训 100 轮也变不出来。

### 9.2 数据采集：GBIF 走不通，改走 iNat 官方 API

先尝试复用现有管线（GBIF），但**失败**：

- GBIF 记录里虽有 `captive_cultivated` 字段，但抽样 5400 条，取值**恒为 `wild`，captive 为 0**
- 原因：iNaturalist 把标记「圈养/栽培」的观察降为 **casual** 等级，而 GBIF 收录的数据集
  名为 `iNaturalist research-grade observations` —— 非 research grade 的根本没被发布
- 另外按 `establishmentMeans` 筛选返回 0（该字段在这批数据里为空），也无法用

改走 iNat 官方 observations API（`captive=true` 筛选），**可行且快**（实测 1~2 秒/次，
`fetch_inat.py` 里记载的「限速 120 秒/页」已不成立）。

新增 `ml/fetch_indoor.py`，采集结果：

| 项 | 值 |
|---|---|
| 采集量 | **3972 张**，20 类，每类 180~200 张（3 类受 iNat 可得量限制：兰花 193 / 绿萝 180 / 铜钱草 199）|
| 输出目录 | `data/plants_indoor/`（**独立存放，不污染原有 2708 张野外图**）|
| 许可 | 全部为 CC0 / CC-BY / CC-BY-NC，逐张署名记录在 `manifest.jsonl`（cc-by-nc 3789、cc-by 145、cc0 38）|
| 域校验 | 抽查确认是室内盆栽（如厨房台面上的盆装绿萝），与用户实拍同一域 |

### 9.3 微调方案：诚实性优先

新增 `ml/finetune.py`，从现有 `best_model.pth` 出发（**微调而非重训**）：

| 项 | 设置 |
|---|---|
| 起点 | `output/best_model.pth` |
| 训练集 | 野外训练部分 2166 + 室内训练部分 2166 = 4332（室内占 50%）|
| 学习率 | `1e-4`（远低于原始训练的 1e-3，避免冲掉已学特征）|
| 轮次 | 12 轮，CosineAnnealing |
| 选优标准 | **野外验证准确率 + 室内验证准确率之和** —— 只涨单边不算好模型 |

**三条保证指标不造假的措施**：

1. **野外验证集复现原切分**（`random_split(seed=42, 0.8)`），那 542 张从未参与训练，
   微调前后可直接对比。实测微调前基线跑出 **0.9096，与初版完全一致**，证明切分复现无误。
2. **室内数据分三段**：train 70% / val 15% / test 15%。val 用于选最优轮次，
   **test 完全不参与选优**，只作最终汇报 —— 避免「用测试集挑模型」的自欺。
3. **类别顺序强制断言**：野外与室内的类别目录顺序必须与 `labels.json` 完全一致，
   否则直接报错退出（顺序不一致会导致标签错位，指标会虚高且毫无意义）。

## 十、42 类模型上线与识别率测试（2026-10-03）

扩类到 42 种（新增仙人球、蟹爪兰、鹿角蕨、一叶兰、幸福树、观音竹、天竺葵、空气凤梨、
非洲堇、果子蔓、吊竹梅、网纹草），骨干网由 MobileNetV3-Large 换成 **EfficientNet-B0**、
分辨率 **320**，全量重训 20 轮。**线上已切换为 42 类 + TTA。**

### 10.1 测试方案（口径与 §2.3 一致）

- **只测未参与训练的图**：复现训练同款切分 —— 室内 `stratified_split(0.70/0.15/0.15, seed=42)`
  的**第三段**（选优未用），野外 `random_split(0.8/0.2, seed=42)` 的验证段。
  随机抽目录会抽到训练图，测出的是"记忆分"，无效。
- **走生产预处理路径**（`recognizer.build_val_transform` + 生产 TTA 三视角），
  不是训练脚本那份 —— 两者一旦漂移会静默降精度。
- 脚本：`tests/eval_recognize_42.py`；线上抽查 `tests/e2e_recognize_42_live.py`。

### 10.2 总体指标

| 测试集 | 单视角 Top-1 | TTA Top-1 | TTA Top-3 | 高置信误判(≥0.80) |
|---|---|---|---|---|
| 室内测试集（1418 张，选优未用）| 0.9231 | **0.9302** | 0.9690 | 14 条 |
| 野外验证集（1238 张）| 0.9459 | **0.9523** | 0.9847 | 6 条 |

单视角 0.9231 与训练记录**完全吻合**，说明上线产物无偏差（ONNX↔pth argmax 一致率 1.0000）。
TTA 较单视角 +0.6~0.7 点。

### 10.3 混淆分析

召回最低的类：观音竹 0.767、绿萝 0.778、幸福树 0.826（室内）；金钱树 0.812、薄荷 0.857（野外）。
混淆对以**叶片形态相近**为主：绿萝↔富贵竹、龙血树↔袖珍椰子、观音竹↔绿萝、常春藤↔铜钱草/天竺葵。

高置信错误（Top-1 判错但置信度≥0.80）是最危险的一类，用户完全无从察觉，共 20 条（室内 14 + 野外 6），
如吊兰→富贵竹 0.94、吊竹梅→万年青 0.93、茉莉花→常春藤 0.96。**Top-3 达 0.97~0.98**，
故对低置信结果建议前端提示重拍、或展示候选供用户确认。

### 10.4 关键发现：识别率的天花板是**数据标签噪声**，不是模型

把 29 张置信度≥0.6 的室内误判导出人工核对（`tests/review_errors_42.py`，图存于 `_err_review/`），
发现**约一半的"误判"其实是数据集标错了**：

| 数据集中的"真值" | 图中实际植物 | 模型判定 | 判定 |
|---|---|---|---|
| 常春藤 | 多肉（莲座状）| 多肉植物 0.86 | **模型对，标签错** |
| 芦荟 | 龙血树 | 富贵竹 0.84 | **模型对，标签错** |
| 吊竹梅 | 万年青/粗肋草类 | 万年青 0.93 | **模型对，标签错** |
| 多肉植物 | 斑马爵床/网纹草 | 网纹草 0.68 | **模型对，标签错** |
| 发财树 | 橡皮树（形态含糊）| 橡皮树 0.84 | 存疑 |

抽查 `常春藤/`（400 张）与 `芦荟/`（200 张）文件夹，各约 **1/4** 明显张冠李戴
（多肉混入常春藤、花园照混入芦荟）——**这些图物理上就存放在错误的类别目录下**（已核对原始路径）。

对**训练集**做置信度审计（`tests/audit_labels_42.py`，找"模型高置信反对其给定标签"的图）：
**6611 张里 0 张**。这个"0"是关键证据 —— **模型已经把错误标签背下来了**，
它从"多肉混进常春藤"的训练图中学会了「多肉 = 常春藤」这一错误关联。

### 10.5 结论与后续建议

1. **93% 已接近当前数据质量的极限**。继续训练、加类、换骨干网都不会改善 ——
   因为错标就是模型正在学习的目标。**真正的下一步是人工清洗数据，而不是加轮次。**
2. **推断真实识别率高于 93%（约 95%+）** —— 一部分"误判"是模型判对、而数据标签错。
   报告呈现时以 93% 为**保守下界**。
3. 数据噪声来源：iNat/GBIF 社区标注（文档已记录其噪声）。清洗需人工复核，
   `tests/audit_labels_42.py` 因"模型已背下错标"而**无法自动定位训练集错标**，
   需改用交叉验证或纯人工抽样。
4. **已知局限**：42 类之外的植物会落到某个已知类上（闭集固有），品种置信度低时提示重拍。
